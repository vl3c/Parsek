## 1. What renders a continuation tail

### 1.1 The predicted tail is ORBIT SEGMENTS, not points

`OrbitSegment.isPredicted` is declared at `Source/Parsek/OrbitSegment.cs:27`. It is stamped true by
`PatchedConicSnapshot.ToOrbitSegment` (`Source/Parsek/PatchedConicSnapshot.cs:508`),
`BallisticExtrapolator.CreateSegment` (`Source/Parsek/BallisticExtrapolator.cs:969`) and the finalizer's
reseed (`Source/Parsek/IncompleteBallisticSceneExitFinalizer.cs:1567`, `:1785`, `:2565`). The single append
into the recording is `IncompleteBallisticSceneExitFinalizer.cs:2681-2682`
(`recording.OrbitSegments.AddRange(result.appendedOrbitSegments)`); `ExtrapolationResult` (`:19`) carries no
point list. **The predicted tail is a pure conic suffix with zero points.**

Serialization: binary `TrajectorySidecarBinary.cs:36` (`OrbitSegmentFlagPredicted = 1 << 0`), write `:644`,
read `:667`; text mirror `TrajectoryTextSidecarCodec.cs:144` / `:174`.
`RecordingTreeRecordCodec` does NOT carry orbit geometry - it travels in the sidecar.

The log confirms the shape for this flight - points did not move, segments did:

- KSP.log:16841 `Predicted orbit-tail reseeded: rec=32ca5546... segmentIndex=0 anchorUT=1078.053 source=TrackSection[14].frames gap=0.400s originalStartUT=1078.453 newStartUT=1078.053 rawMeters=134.42 residualMeters=0.00`

**No render-path consumer excludes a segment because it is predicted.** `ForwardRenderWindow.cs:197-199`

### 1.3 Map polyline - owns recorded points, plus an additive forward-arc pass

`BuildLegsForRecording` (`Display/GhostTrajectoryPolylineRenderer.cs:2984-3138`) draws **recorded points
only**, minus every UT an above-surface `OrbitSegment` claims (`:2990` `ComputeOrbitalCoverIntervals`,
`:3016-3038` per-section, `:3042-3054` flat-list fold-in guarded by `IsInsideAnySection`). So the polyline is
correctly NOT responsible for the predicted arc itself.

But the Driver also renders an additive predicted-path surface. `:4400` names it: "the additive FORWARD legs
/ forward arcs / seam bridges (predicted-path surfaces)". That pass is gated by
`SelectForwardArcSegmentIndices` (`:3384`), and it skips below-surface conics:

```
internal static bool IsOrbitSegmentBelowSurface(OrbitSegment segment, BodySurfaceProvider surface)   // :3269
{
    ...
    double periapsisRadius = segment.semiMajorAxis * (1.0 - segment.eccentricity);
    return periapsisRadius < info.radius;                                                             // :3276
}
```

Three consumers drop the segment on that predicate: `ComputeOrbitalCoverIntervals` (`:3301`),
`SelectForwardArcSegmentIndices` (`:3384`), `HasForwardArcCandidate` (`:2339`). The stated intent is at
`:3341-3343`: such a descent "is drawn as a forward LEG (B'), not an arc (Step 3 / FIX #27)", with the leg
built from the recorded descent samples the excluded cover no longer swallows (`:3283-3291`) plus
`FillFramelessGapsFromConics` (`:2933`) re-sampling the conic's shape into gaps.

**That is where it breaks.** The filler's loop is
`for (int i = 0; i < originalCount - 1; i++) { var p = pts[i]; var q = pts[i + 1]; ... }` (`:2934-2937`) -
strictly interior, between two consecutive recorded points, with `GapFillMinSeconds = 15.0` (`:2895`) and
`GapFillMaxPointsPerGap = 30` (`:2898`). A tail conic starting after `pts[last]` has no bracketing `q` and
is never sampled. Excluded from the arc pass, no points for a leg, no gap to fill: **nothing is drawn.**

The seam machinery would have handled the boundary had an arc survived: `IsBridgeAdjacentConic`
(`:2213-2221`) is UT-adjacency and same-body only, with `BridgeMaxSeamGapSeconds = 120.0` (`:1993`),
`BridgeSeamSharedBoundaryToleranceSeconds = 1.0` (`:2001`), and the four-band angle gate
`ClassifySeamBridgeByAngle` (`:2058`) over `BridgeMaxAngleRadians = 0.785` (`:1986`),
`BridgeMinAngleRadians = 0.0873` (`:2015`), `BridgeChordMinAngleRadians = 0.00873` (`:2029`),
`BridgeMergeSampleCount = 60` (`:1980`). The Driver's bridge search (`:6200-6232`) skips
`IsOrbitSegmentBelowSurface` at `:6209` but does **not** skip predicted segments - so a predicted tail is a
legitimate bridge target, and the subsurface predicate is again the only thing in the way.

### 1.5 The intended contract, and what a healthy boundary looks like

The four surfaces are meant to tile one path with no overlap and no gap. The flight ghost plays recorded
points to the last authored sample then hands off to the predicted conic with a 5-10 s continuity blend. The
polyline owns exactly the complement - recorded samples not claimed by an above-surface segment - so the
predicted tail is deliberately the **orbit line's**, not the polyline's; the polyline only borrows a
below-surface conic's curvature between two bracketing samples and bridges the leg/conic seam by UT
adjacency. The proto orbit line draws the tail as a clipped Keplerian arc. The TS shows the same thing by
the same code.

The healthy shape is visible in this same log on the probe fork:

`isPredicted = False` (section 3), and the arc drawn is the near-circular recorded checkpoint conic.
