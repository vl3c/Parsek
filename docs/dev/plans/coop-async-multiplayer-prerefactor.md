# Cooperative Async Multiplayer - Pre-Implementation Refactors

*Refactors to land BEFORE the multiplayer tasks that need them, so the feature fits the existing seams with fewer guards, no duplicated orchestrations, and smaller blast radius. Derived from four code investigations on 2026-09-02 (store registration + fence; ledger orchestration; spawn ownership + consume route; ERS composition + test infrastructure).*

**Status:** PLANNED. Companion to `coop-async-multiplayer-tasks.md` (task ids below refer to it) and the design doc `docs/dev/design-coop-async-multiplayer.md`.
**Branch:** every item lands via its own sub-branch PR into `coop-multiplayer` (never `main`), before the task it unblocks.

---

## Principles

1. **Additive first.** Most items add a seam and leave every existing caller byte-identical (thin forwarders, preserved tuple overloads, new methods). Those can ride together in small PRs.
2. **Behavior-changing items get their own PR, a CHANGELOG line, and a named regression cell**, landed with the existing suites green BEFORE any multiplayer code depends on them. There are exactly three: A4 (exclusion composition unification, a per-frame path), C3 (`SpawnTreeLeaves` through the gate), and B2's consumers (once-ever dedup changes solo career derivation on saves carrying duplicate rows).
3. **Pin, then move.** Where a seam is covered by many existing tests (the spawn gate: ~112 call sites asserting reason strings; the recalc overloads: a flag matrix), the refactor first adds a table-driven pin test of today's behavior, then restructures under it.
4. **Do not build abstractions the fold does not need.** Several tempting generalizations were evaluated and rejected (section "Explicitly not doing").

Sizes: S (one session, 1-2 files), M (one session, 2-4 files), L (split at plan time).

## Corrections to `coop-async-multiplayer-tasks.md` surfaced by the scans

- **M2.3 (optimizer freeze) names a dead method.** `RecordingOptimizer.CanAutoSplit` (:163) is not on the optimizer path; `RunOptimizationSplitPass` uses `CanAutoSplitIgnoringGhostTriggers` (:189). And `RunOptimizationPass` (`RecordingStore.Optimization.cs:23`) has five sub-passes: a merge/split-only freeze leaves two that rewrite exported bytes - `TrimBoringTailsForOptimization` (:408, `FilesDirty` at :432) and `EnsureCheckpointSectionsForTopLevelOrbitSegments(..., markDirty: true)` at `RecordingOptimizer.cs:619`, which mutates during candidate DISCOVERY before any boundary predicate. Correct shape: one `RecordingOptimizer.IsOptimizationFrozen(rec, out reason)` consulted at four sites (`CanAutoMerge` beside the supersede guard :66, the loop head of `FindSplitCandidatesForOptimizer` :629 AND its :619 normalization call, the loop head of `TrimBoringTailsForOptimization` :422). Purely additive.
- **The "optimizer never bumps StateVersion" claim is false as stated.** `BumpStateVersion` IS called at `RecordingStore.Optimization.cs:85` (post-`RemoveAt`) and `:204` (post-`Insert`); the documented contract (`RecordingStore.cs:496-502`) is list MEMBERSHIP only, which those satisfy. The real gaps are content mutation without a bump (tail trim, `PopulateLoopSyncParentIndices` :567, discovery-time normalization) and the absence of engine reindexing on the mid-list insert. The separately filed fix for this should be re-scoped to those two.
- **M2.6 registration** becomes "call `RegisterCommittedTreeCore` with flush/baseline/milestone off" (A1), not "mirror the CommitTree shape". Importer ordering constraint: place sidecars, register trees, THEN any load-time sweep; `CleanOrphanFiles` (`RecordingStore.OrphanCleanup.cs:345`) quarantines any sidecar id absent from `BuildKnownRecordingIds` and runs at `ParsekScenario.cs:4153` after tree load. Sidecar placement can reuse `SidecarFileCommitBatch.StageWrite(path => File.Copy(src, path, true), finalPath)` as-is (content-agnostic; reverse-order rollback). Validate in the packet dir with the existing read-only probes (`RecordingStore.TryProbeTrajectorySidecar` :6798, `TrajectorySidecarBinary.TryValidatePayload` :183, `RecordingStore.TryLoadSnapshotSidecar` :6964), copy, then hydrate through the ordinary `LoadRecordingFiles`; do NOT use `AreRecordingFilesCurrentAtPaths` (:730) as the packet gate (it answers "is this what I would write", not "is this loadable").
- **M2.2 fence** routes through A2's gate plus the ~11 existing chokepoints; "recording rename" is not a surface (no `rec.VesselName =` outside the codec); the mission-level loop writes (`MissionsWindowUI.cs:4231`, `MissionStore` :521/532/568/577/765) and three internal policy clears (`ParsekFlight.cs:16763-16765`, `RouteTreeGuard.cs:213`, `RecordingStore.cs:4586`) need a one-line decision each.
- **M4.1 is stronger than "mirror `CreateSplitBranch`".** The split path copies a snapshot only when the parent's is null (:5585-5592); M4.1 must OVERWRITE the closing parent's `VesselSnapshot` (ghost geometry reads the separate `GhostVisualSnapshot`, so appearance is unaffected). `pendingDockSelfSnapshot` is already read inside `CreateMergeBranch` (:6372, route-proof block) and cleared after the call (:12377, :12294), so the stamp is a two-line addition at step 2. Two additions: the BACKGROUND parent needs `pendingDockPartnerSnapshot` gated on `pendingDockPartnerSnapshotPid == bgParentRec.VesselPersistentId`; both captures happen only while `data.from.vessel != data.to.vessel` (the retroactive path :11050-11095 documents the null), so the stamp is conditional and the segment-start fallback stays load-bearing.
- **M4.5 needs an explicit ledger-masking decision.** Design 7.8 step 4 says masked recordings "nor feed the ledger", but `ComputeELS` is documented (`EffectiveState.cs:1451-1453`) as having NO recording-level filter: retirement is expressed only as per-`ActionId` `LedgerTombstone` rows. Options: derived (non-durable) tombstones minted by the fold, or a recording-id exclusion in `ComputeELS` keyed on `MaskStateVersion`. Recommendation: the recording-id exclusion (deterministic, derived, no fake durable rows), with the ELS contract comment updated to "tombstones OR fold masks". Recorded in the design doc 7.8.
- **M4.5 must also cover the sixth spawn path** (C3) or the fold's masks are bypassed by post-commit leaf spawning.
- **M4.11** is `StartStandaloneContinuationSegment` + one field after C6; no dispatch-into-pure-core refactor.
- **M3.4's "merge recalcs pass authoritativeReduction"** has no parameter to pass today; it exists only after B1.

## Explicitly not doing (evaluated and rejected)

| Idea | Why not |
|------|---------|
| Full `SpawnOwnershipResolver` replacing the emergent leaf rule across all hosts | L / high risk: 112 pinned call sites asserting reason strings, a live cross-predicate drift guard, host-specific ANDs that are scene capabilities not ownership (`currentUT < EndUT`, `kscSpawnAttempted`, KSC's Orbiting/Docked defer). The fold's needs are four new early rejects on the existing ladder (C2) plus C1 and C3. Revisit only if the ladder proves inadequate after M4 |
| `IEffectiveExclusionSource` polymorphic list | Heterogeneous sources (a cascade closure, a marker-identity closure, a flat set) on a per-frame locked static cache; a fixed 3-source funnel with a 4-field key is the honest shape (A4) |
| `ScenarioNodeCodec` extraction | `SaveStagingList`/`LoadStagingList` are already generic; extracting from the 8,346-line `ParsekScenario.cs` touches OnSave/OnLoad for no new capability. Copy the pattern; prefer `TryLoadFrom` for the new singleton nodes |
| `StaticStoreSnapshot` capture/restore for two-machine tests | Static stores make true coexistence impossible; `RecordingStoreTestSnapshot` is deliberately shallow. Sequential `MachineContext` resets are the honest model (A6) |
| Reconcile policy object | `Ledger.Reconcile` has two callers reading one local (`LedgerOrchestrator.cs:2698`); the campaign override is one disjunct; the per-scene rule is three pure lines with two consumers |
| Persisted global `Sequence` allocator | `Sequence` is already a per-batch/per-session ordinal; a persisted high-water allocator would reorder existing saves' same-UT rows (a live derivation change) for no multiplayer benefit. The `(OwnerPlayerId, ActionId)` tiebreak is total regardless; add the frozen-row guard at the five mutation sites (`LedgerRolloutAdoption` :93/:355/:391/:431, `LedgerRecoveryFundsPairing`) |
| Deferred-patch flush QUEUE | The walk is stateless; replaying a queued patch equals recalculating; the trigger set already covers every deferral-clearing transition. Only the observability flag (B3) is worth it |
| Sharing the registration core with `LoadRecordingTrees` | Its needs are the strict subset `AddCommittedInternal` already covers; cosmetic payoff against real cold-load risk |
| Moving consume-route dispatch into `SwitchSegmentConsume` | Would add three collection parameters to the pure signature and touch a seam four routes and a patch depend on, to save one `if` |
| `RosterMaterializer` as a pre-refactor | M5 is far out; do it inside M5.1 |
